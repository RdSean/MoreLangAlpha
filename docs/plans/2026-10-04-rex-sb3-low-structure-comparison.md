### 时间为何没有随输出减少

1. 响应等待明显变长。可见 19 个完整 LLM span 合计 318.572 秒，不能当作全程模型时间。其中 16 个有 first_token_time，首 token 等待 1.602–25.841 秒，累计 129.027 秒；同一 16 个调用的总 span 时间 244.829 秒，首 token 等待占约 52.7%。high 有记录的 31 个首 token 延迟为 0.148–1.062 秒。例：low 一轮 26.598 秒、仅输出 262 tokens，但首 token 等待 25.841 秒。能证实等待增大，不能从这些指标区分服务商排队、内部计算、网关或网络。
2. 调用和返工增多。high 只有 1 次 Edit；low 有 12 次，其中章节脚本 5 次、知识点脚本 7 次。模型修正 children/边界、标题位于正文内部的层级关系、知识点备用 node 引用、标题截取和过滤规则，多次重建、检查和重新合并。输出少了不代表步骤少了。
3. checkpoint 提供缺失尾段的时间证据。每条模型消息对应的父 checkpoint 到直接子 checkpoint 窗口合计 low 588.988 秒、high 341.592 秒。这个窗口包含模型节点、middleware 和 checkpoint 开销，不等同于精确 LLM span；与 high 完整 LLM 合计 339.907 秒接近。low 的耗时主要位于模型节点窗口，而非约 12 秒准备或末尾提交，不能把全部慢归因于 MinIO/Docker 文件复制。

## 结构与语义质量抽查

本轮 312 个递归节点、12 单元、108 知识点，仍为每单元 9 条；high 是 308 节点/108 知识点。最终 validation_warnings 为空，最后校验报告 L1/L2/L3 均 0，content_file 均 null。格式通过不等于语义质量通过。

恢复 Agent 实际写入并按顺序 Edit 的 build_kps.py，可见 pick_split 按行区间中点寻找标题/段落候选，title_for 优先用四级子标题，否则 snippet 截取 46 字符，缺内容时用“本节内容”。这不是逐知识点深入语义命名，解释了下列可复核问题：

- u02-k06 标题含“Review this reading skill in Unit 2A”，其源区间 1073–1083 实为 ANALYZING CLAIMS 及三个短答题，标题截到了练习说明。
- u06-k06 标题含“study conducted by researchers at 1 • groups w”，源区间 3082–3098 是研究笔记补全题，不是可读的知识点名称。
- u03-k06/u11-k06 的标题尾部为“本节内容”，缺少具体学习目标。
- u01-k01 为 267–321，已包含 A Love for Soccer 的 E/F 段；u01-k02 从 323 的 G 段开始，却命名 SOCCER WITHOUT BORDERS，其信息图标题实际在 339。正文段落与信息图之间的切分/命名错位，可影响后续讲义范围，不只是 UI 文字问题。
- u12-k09 为 6130–6244 的视频知识点，纳入 6203 起版权清单和 6219 起致谢；coverage.excluded 又声明排除 6203–6245，两者矛盾。单元尾边界/知识点块选择需要语义复核。
- u12-k04 写“Prefix -ize”；源目录表第 136 行本身也写 Prefix，但实际词汇练习第 5909 行写 suffix -ize。属于原文内部冲突没有被消解，不能简单归类为无来源幻觉。

这些是确定的本轮抽查发现，不据此推导整书错误率，也不宣称它们一定由 low 导致。high 尚未做同等逐项内容核查。coverage 的图片文字缺失/答案缺口仍是 Agent 声明，不代替独立视觉验收。
